# 待办分组（多个 todolist）设计

> 用户原话：「还有，todolist，也放到右边」→「每个todolist给区分开，这里3个list，都显示到一起了」

## 0. 实测事实（不是推断）

每条都附了命令与输出。设计里凡是依赖这些事实的地方都标了出处。

### 0.1 待办**不落盘**

```
$ node /tmp/chk.cjs
FILE 20260811-111712-db5b068e.json
顶层 keys: version,id,title,titleManual,titleGenerated,cwd,model,createdAt,updatedAt,messages,totalUsage,checkpoints,compaction
含 todos 字段? false
```

会话 JSON 里没有 `todos`。`SessionManager` 的 `private todos: TodoItemLite[] = []` 是纯内存态。

**推论**：本次改动**没有数据迁移问题**——不存在需要兼容的历史数据。反过来说，
刷新页面/切回旧会话时待办面板本来就是空的（我在真浏览器里踩到过，一度以为是 bug）。
分组不会让这件事更糟，但也不会顺手修好它。**明确不在本次范围内。**

### 0.2 现状：模型只能用 emoji 前缀假装分组，**而且它自己会认错组**

用户会话 `20260811-111712-db5b068e.json` 里**第 5 次**（共 8 次；第 7、8 次是后来做的
A/B/C 冒烟测试，与本议题无关）TodoWrite 的实际入参：

```
🚀 项目A - 前端重构：完成首页响应式布局   in_progress
🚀 项目A - 前端重构：接入新的组件库       in_progress
🚀 项目A - 前端重构：优化首屏加载速度     in_progress
🍳 生活琐事：去超市买菜（西红柿、鸡蛋、牛奶）  pending
...
📚 学习计划：读完《设计模式》第5章        completed
```

模型自己在回复里说明了原因：「目前 TodoWrite 只有一个全局列表，没法拆成3个独立的
todolist。我用 emoji 前缀做了视觉分组」。**这是模型在替工具的缺陷打补丁。**

代价有两层，**第二层才是真正的理由**：

1. **排版**：每条正文都被组名占掉一截，而右栏窄（用户截图里「去超市买菜（西红柿、鸡蛋、
   牛奶）」已经折行）。
2. **正确性 —— 模型会认错组。** 用户 `11:23` 的原话是
   **「你怎么能判断成是项目A呢？？？？」**。因为组的归属只存在于**模型自己发明的前缀字符串**里，
   每次「把第 N 组都改成 X」它都要重新解析那些前缀去定位子列表，而它解析错了。

第 2 条把这件事从「排版不好看」抬成了「会做错事」。设计的价值主要来自这里 ——
把组的归属从**正文里的约定**变成**结构化字段**，模型就不必再解析自己的字符串。

## 1. 方案取舍

### 选中：给每条待办加一个可选的 `group`

```ts
export interface TodoItem {
  content: string
  status: TodoStatus
  /** 可选分组名。缺省 = 不分组（与今天完全一致）。 */
  group?: string
}
```

**为什么是它**：0.3 那张表里有 6 个消费方。可选字段意味着**不改的那些照样正确**——
TUI 不认 `group` 就还是平表，行为与今天一字不差；压缩提示词、快照、清空逻辑
全都不用动结构。换成嵌套结构（`lists: [{name, todos}]`）则这 6 处必须同时改，
而其中 `tui/App.tsx` 与本次用户诉求（web 右栏）毫无关系，纯属被牵连。

**代价（要认）**：
- 扁平表示允许**同名分组不连续**（A、B、A）。渲染必须按「首次出现」归拢，
  否则会出现两个同名分组。这是嵌套结构天然没有的问题。
- 模型可能**根本不填** `group`。工具描述里得写清楚什么时候该填；但不能强制，
  否则单一任务列表这种最常见的场景反而被逼着编一个组名。
- 组名重复了正文里的信息时（模型既填 group 又保留 emoji 前缀），会看着啰嗦。
  **不做自动去前缀**——那是猜用户意图，猜错了更难解释。

### 落选：嵌套的多列表结构

概念上更干净，每个列表天然有自己的进度。但要动 6 处消费方 + 协议破坏性变更，
而收益仅仅是「同名分组不可能不连续」这一个边界情况。**不值。**

### 记录在案、本次不做：让 TodoWrite 支持按组的**局部更新**

`TodoWrite({ group: '项目A', todos: [...] })` 只替换该组。评审提出，本 spec 初稿漏了这条。

**它同时命中两件事**：子代理只能覆盖自己的组（§2.4c 那个坑自然消解）；
用户说「把项目A都设成完成」时模型不必重发全部 9 条 —— **而重发正是它出错的地方**（§0.2）。

**为什么本次仍不做**：TodoWrite 会从「整份覆盖」变成双语义工具，模型每次要判断用哪种模式，
「删掉整组」需要新约定，而且它与 §2.3「不做强制校验，因为整份覆盖下报错代价大」的
论证前提直接冲突 —— 那条论证在局部更新语义下不再成立。这是**真正的复杂度增加**，
不该和「加个可选字段」捆在一次改动里。

**但它是 §2.4c 的天然解。** 如果剥掉子代理的 TodoWrite 之后发现子代理确实需要任务跟踪，
这是唯一的出路，届时按这条走，别另发明第三种。

### 落选：什么都不做，把 emoji 前缀写成约定

零代码。但 0.2 已经证明这条路的代价由**正文宽度**承担，而右栏本来就窄；
且模型每次都要自己发明前缀，不同会话不一致。用户明确提了这个问题，不该敷衍。

## 2. 具体行为

### 2.1 渲染（web 右栏）

- 有 `group` 的按**首次出现顺序**归拢；无 `group` 的归入一个隐式的「未分组」桶。
- **隐式桶排在最前**：它对应「没有分组需求」的普通用法，不该被有组名的挤到下面。
  **代价要认领**：模型若给前 4 条填了 group、第 5 条漏填，第 5 条会**跳到列表最顶端**。
  「漏填 = 置顶」是刻意接受的结果 —— 另一种做法（漏填的留在原位）会让隐式桶被切成
  好几段，更难解释。
- 每个分组一行小标题：`组名   n / m`。
- **分组不得引入包裹元素**：用 `<Fragment key={g}>`（不产生 DOM），隐式桶不渲染标题。
  这是上面「逐字节一致」能成立的**唯一实现路径** —— 直觉写法 `<div className="todo-group">`
  会当场把那条约束打掉。（CSS 那边其实无所谓：`styles.css:379-388` 全是后代选择器
  `.todos .ti`，加个包裹层样式不会坏；坏的只有逐字节一致。）
- 面板顶部保留原有的全局 `已完成 / 总数`——它回答「整件事还剩多少」，
  分组小计回答「这一摊还剩多少」，两个问题都真实存在。
- **全部无 `group` 时，渲染结果必须与今天逐字节一致**（不出现「未分组」标题）。
  这是本设计里最重要的一条兼容性约束，要有测试钉住。

### 2.2 可见性

`hasVisibleTodos` 的现有语义**不改**：一条都没有 → 隐藏；全部 completed → 隐藏。

**明确不做**「某个分组全完成就隐藏该组」。理由：分组在对话中途凭空消失比多占几行
更让人困惑，而且会让「3 / 9」这类全局计数对不上眼前看到的行数。
**代价**：一个早就做完的分组会一直占着位置。接受。

### 2.3 每组至多一条 in_progress

工具描述现在写的是「Only one task should be in_progress at a time」。分组之后这句话
**字面上有歧义**（是整份列表一条，还是每组一条？），必须挑明。改成**每组至多一条**。

**为什么挑明成「每组一条」而不是「全局一条」**（这个方向此前两稿都没写）：
分了 3 组本身就意味着「同时推进 3 摊活」。全局单条等于**禁止并行推进**，直接违背分组的初衷。

**会话数据的实际情况**（第三稿据实写出，不再概括）：

  但这是**我的解释**，不是数据自己说的话。

唯一自发的数据点只有 `#1`，而 `#6` 与规则冲突且只能靠解释化解 —— 太薄了。
规则的依据只有上面那条方向性论证。

> **三次认账，同一段。**
>
> 初稿写「模型把学习计划三条同时设成 in_progress，说明它不遵守全局单条约定」——
> 错在那是用户 `11:20` 下令的结果，我把用户的指令读成了模型的天性。
>
> 第二稿改成「不引用任何会话数据」，却在紧接着的一句里断言「那几次同时 in_progress 的
> 条目**都在同一组内**」—— **这句是假的**（`#1` 就跨组），而且它本身就是在引用会话数据，
> 与前一句自相矛盾。更糟的是 `#1` 恰恰是全部数据里唯一相关的证据点，
> 方向还支持这条规则，我在"认账"时把它漏掉，然后用一句错的概括把整段数据判成了无效。
>
> **第三次。** 第三稿把真实输出贴了出来，但**只贴到 `#5` 就截断**，块头却写着
> 「该会话 8 次 TodoWrite 全量」，也没有省略号。被截掉的 `#6` 恰好是全部数据里**唯一**
> 与「每组至多一条」冲突的点。这次没有假陈述（展示的每条都对得上），
> 但机制与前两次一模一样，而且这回被概括掉的是**反面证据**。
>

> 而不是先把数据完整读出来再看它支持什么。
> **可操作的规则：凡是 `$ 命令` 下面的块，必须是该命令的真实完整输出；
> 需要节选就去掉 `$` 提示符、明写「以下为整理后的清单」。**

**不做强制校验**：工具不会因为两条 in_progress 就报错。原因是 TodoWrite 是
「整份覆盖」语义，报错会让模型丢掉整次更新，代价远大于显示上多一个圆点。

### 2.4 组名的界限

- 非字符串 / 空串 → 当作没填（落入隐式桶）。
- 长度上限 **60 字符**，超出截断。理由：右栏标题只有一行，更长的组名要么折行
  要么撑破布局；而组名本就该是短标签。
- **不限制分组数量**。模型分出 20 组是它自己的表达问题，工具不该替它做判断；
  面板是可滚动的。

### 2.4b 工具回显必须带上分组（**头号风险的真正杠杆**）

`tools/todo.ts:62` 现在拼的是：

```ts
const lines = validated.map((t) => `${icons[t.status]} ${t.content}`)
```

**这串字符串是模型看到的工具结果。** 而 TodoWrite 是**整份覆盖**语义 —— 模型每次都要
从自己的上下文里重建整张表。回显里若没有 `group`，模型手上**最新、最显眼的那份记录
就是没有分组的**，下一次调用极可能退回平表。

这与 §2.5 的压缩提示词是同一类漏洞（分组信息在某条回路上蒸发），但更致命：
压缩几十轮才发生一次，回显**每次调用都发生**。

格式与压缩提示词保持一致（`[组名]` 分段）。**三种情形都要定义**（前一稿只定义了两种，
而漏掉的第三种正是分组最可能蒸发的地方）：

| 输入 | 回显 |
|---|---|
| 全部无 `group` | **一字不变**（今天的格式） |
| 全部有 `group` | 按首次出现顺序，每组一个 `[组名]` 段 |
| **混合** | **未分组的先出，不带任何标题**；其后才是各 `[组名]` 段 |

混合档刻意与 §2.1 的面板一致（隐式桶置顶、无标题）—— **两处排序规则必须同一套**，
否则模型看到的顺序和用户看到的顺序不一样，它下次重建列表就会按错的那套来。

**收尾那行 `(n/m completed)` 不要动位置**：`toolSummary.ts:12` 的
`TRAILING_NOTE_RE = /\n+…?\[[^\]]*\]\s*$/` 会剥掉输出**末尾**的方括号注记。
现在因为末行恒是 `(n/m completed)`，组标题永远落不到末尾，所以不会被吃掉 ——
但把那行挪走，最后一个 `[组名]` 就会被静默剥掉。

§2.5 的压缩提示词同此三档。

## 6. 风险

**最大的风险不是代码，是模型到底会不会用这个字段。** 加了字段，模型仍可能继续用
emoji 前缀——那样这次改动就是白做。落地最后一步必须真跑确认，不能只看测试绿。

**两件不同的事，不是「三根按力量排序」**（前两稿的排序是没有依据的，且把 schema 判低了）：

| 职责 | 靠谁 | 说明 |
|---|---|---|
| **首次使用**（bootstrap） | **schema 字段描述 + 示例** | **模型不可能填一个它不知道存在的字段。** schema 是 `group` 存在性的**唯一**声明处，是必要条件，不是"最弱的那根"。工具定义和系统提示词一样每轮都在上下文里，不存在「只在决定调用时才被读到」这回事 |
| **跨轮保持**（persistence） | **工具回显**（§2.4b） | 整份覆盖语义下模型每次从回显重建列表。回显再强也**引导不了第一次调用** |

压缩提示词（§2.5）是 persistence 在超长对话上的延伸，同一职责。

### 6.1 系统提示词那条路：**放弃，并说清为什么**

前两稿把 `core/prompt.ts` 的 `<task_tracking>` 当作第二强杠杆。**实测证明这条路对
Claude 系模型是静默归零的**：

```
$ grep -n "task_tracking" packages/core/src/prompt.ts
82:<task_tracking>
86:</task_tracking>
$ grep -n "NON_CLAUDE_ENFORCEMENT_OVERLAY\|isClaudeFamily" packages/core/src/prompt.ts
41:export const NON_CLAUDE_ENFORCEMENT_OVERLAY = `
100:export function isClaudeFamily(modelId: string): boolean {
151:  const overlay = modelId && !isClaudeFamily(modelId) ? `\n${NON_CLAUDE_ENFORCEMENT_OVERLAY}` : ''
$ grep -n "TodoWrite" packages/core/src/prompt.ts
83:For multi-step tasks (3+ steps), use the TodoWrite tool to create a task list BEFORE
```

`<task_tracking>`（82-86）整块在 overlay（41-97）里面，`:151` 只对**非 Claude** 模型追加。
而且 **`TodoWrite` 在整个 prompt.ts 里只出现在第 83 行** —— `DEFAULT_SYSTEM_PROMPT`
从头到尾没提过这个工具。

于是两条路都不好走：

- 写进 overlay → Claude 系模型收不到，**且没有任何测试会红**（静默）；
- 写进 `DEFAULT_SYSTEM_PROMPT` → 全模型生效，但要在一个**从未提过 TodoWrite** 的提示词里
  凭空插一段讲某个工具的字段，位置突兀；且它会改动被 prompt cache 缓存的前缀
  （`prompt.ts:152` 的注释明确在意这件事）。

**定案：不动系统提示词。** 引导全部走 schema 描述 + 回显。

依据是 `prompt.ts:11` `DEFAULT_SYSTEM_PROMPT` 开篇自己写的那句：
*"Each tool's exact inputs and behavior are described in its own definition."*
—— 字段级的说明本来就该长在工具定义里，这是本仓库既定的分工。

**订正一处**：前一稿说 schema 路线「零 cache 代价」，**讲反了**。
`anthropic-client.ts:55-65` 给最后一个工具定义挂了 `cache_control`，:72 给 system 也挂了；
渲染顺序是 `tools → system → messages`，失效是前缀式的 —— 改**工具定义**会让三层全失效，
改**系统提示词**只失效 system + messages。所以 schema 路线的 cache 代价**严格更大**。
结论不变（两者都只是发版时一次性冷写，不是每请求成本），但理由换成上面那条。

**代价**：弱模型少一层强制。若真跑发现非 Claude 模型确实不填，**那时**再往 overlay 里加
一句 —— 那是给弱模型打补丁，不是主路径。这个顺序比反过来好：先看主路径够不够，
不够再加特例。

### 6.2 组名是自由字符串，近似写法会裂

`group` 每次都要模型**逐字复现**（整份覆盖语义），而 §2.1 的归拢是精确字符串匹配。
于是「项目A」/「项目 A」/「项目Ａ」会裂成两个标题 —— 症状与今天 emoji 前缀错乱**同源**，
只是频率低些。

§0.2 说「变成结构化字段，模型就不必再解析自己的字符串」—— **只对了一半**：
解析的负担没了，复现的负担一点没减。

处置：`group` 先 `trim()` 再判空（纯空白视为未填）。**不做**模糊归并（大小写折叠、
全半角归一）—— 那是猜，猜错了两个真正不同的组会被合并，比裂开更难发现。

**真正的解是「记录在案、本次不做」那条按组局部更新**：局部更新下模型只需要说出一次组名，
不必每轮复现。这条风险是那个方案价值的又一个论据。

若真跑之后模型仍不用这个字段，说明问题在别处（比如它没意识到用户要分组），
**不加强制校验** —— 强制会让一次正常的单列表更新直接失败。
