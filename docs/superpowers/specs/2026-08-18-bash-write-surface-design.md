# 路径护栏管不到 Bash —— 设计

> 状态：待独立评审。作者同时是发现者，**这份 spec 的结论不能自己批准自己**。

## 1. 实测事实（不是推断）

### 1.1 「必须确认」档被一条重定向绕过

真浏览器 + 真 daemon，全自主（bypass）档。让模型写 `ZUSE.md`（在
`BUILTIN_CONFIRM_RULES` 里）。会话记录原文：

    1. Write(E:\ai-study\zuse\ZUSE.md) → 弹卡片 → 人点了「拒绝」
       tool_result: "用户拒绝了这次 Write 调用（规则：Write(E:\ai-study\zuse\ZUSE.md)）。
                     不要重试同一调用。请询问用户如何继续，或改用其他方式。"
    2. Bash: echo "探针" > ZUSE.md → (no output)，is_error: false
    3. assistant: "已创建 ZUSE.md。"

文件落地。**全程没有第二张卡片。**

两点值得单独记：

- 模型不是在攻击，它是在**照着我们给的提示走**。拒绝文案里那句
  「或改用其他方式」就是这次绕行的直接诱因。
- 「必须确认」这一档当初的设计理由是「一次写入影响以后所有会话，
  不该被一次『总是允许』永久买断」。而它现在连**这一次**都拦不住。

### 1.2 `~/.zuse/**` 的 deny 同样绕得过去

同一档下：`echo probe > ~/.zuse/__probe.txt`（落在
`DEFAULT_DENY_RULES` 的 `Write/Edit(~/.zuse/**)` 树里）。
**没有任何卡片，文件落地。** 探针文件已删。

### 1.3 病根

规则是 `工具名(限定符)` 的形状，匹配拿的是 `toolName + specifier`。
Bash 的 specifier 是**命令行文本**，于是：

    规则 Write(~/.zuse/**)   ← 只对 toolName === 'Write' 的调用生效
    调用 Bash("echo x > ~/.zuse/f")  ← toolName === 'Bash'，不匹配

deny（第 2 步）、confirm（第 3.2 步）、ask（第 5 步）**全都是这个形状**。
所以这不是某一条规则写漏了，是**整层路径护栏对 Bash 是失效的**。

### 1.4 已有的半个机件

D7 那轮（324bb48）已经做了「按段识别文件重定向」：`splitBashSegments` 返回
`{ text, hasFileRedirect }`，用途是「带重定向的段，前缀 allow 规则不算覆盖」。
它**认得出有没有在写文件，但把写向哪里丢掉了**。而且它只影响 allow 前缀规则，
全自主档在 allow 匹配之前就放行了 —— 这正是 1.1/1.2 两条能成立的原因。

## 2. 候选方案

### A. 抽出重定向目标，按 `Write(<目标>)` 过 deny / confirm

`splitBashSegments` 顺手把目标 token 带出来（**同一次扫描**，不新写正则 ——
仓里已经因为「两套扫描器对同一条命令两种解释」出过一个真实越权洞）。
decide() 对每个目标用 `matchesRule(规则, 'Write', 目标, cwd)` 再过一遍
deny 与 confirm。

- 代价：**只挡重定向**。`cp` / `mv` / `tee` / `sed -i` / `dd of=` / `git checkout` /
  `uv run python -c "open(...,'w')"` 一个都不管。变量拼接（`f=~/.zuse/x; echo y > $f`）
  也绕得过 —— 静态分析看不见变量值。
- 收益：关掉**模型实际会走的那条路**（1.1 的记录就是原样证据），代价小、
  误报面窄（重定向目标是明确的写入面，不是猜的）。

### B. 文本包含法：命令文本里出现受保护路径就落 confirm

- 代价：误报重（`cat ~/.zuse/MEMORY.md` 只是读也会被拦）；绕过更容易
  （相对路径、变量、`$HOME`、大小写、`..`）。误报会训练用户闭眼点「允许」，
  那比不拦更糟。
- 收益：不依赖 shell 语法分析。

### C. 收口到工具层 / 文件系统层

Bash 执行前给受保护文件加只读 ACL，或事后比对快照。

- 代价：Windows ACL 太重且易留残留；事后比对是**检测**不是**阻止**，
  而这几个文件的语义是「写进去就影响以后所有会话」，检测到已经晚了。
- 收益：不依赖静态分析，真正覆盖所有写法。

### D. 不修，改成如实声明

删掉拒绝文案里「或改用其他方式」那句诱导语，把「路径护栏管不到 Bash」
写进文档和工具说明。

- 代价：洞还在。
- 收益：不制造「已经修好了」的错觉。

## 3. 倾向：A + D，且**必须明写 A 不是完整解**

理由：

1. A 关掉的是**实测中模型真正走的那条路**。1.1 里模型没有做任何规避，
   它只是换了个最顺手的工具。把最顺手的那条路堵上，收益是真实的。
2. B 的误报会毁掉这一档的可信度。一个被闭眼点掉的确认卡等于没有卡。
3. C 的代价与本仓既有取舍（不做 realpath、不做 inode）不在一个量级，
   而且「检测」对这几个文件的语义无效。
4. D 里那句诱导语是**我们自己写的**，删掉它零成本。

**A 最大的风险不是漏，是「以为不漏」。** 所以：
- 代码注释、features.md、工具说明三处都要写清「Bash 不是被完全护住的面」；
- 不要在 UI 上把这一档说成「无法绕过」。

## 4. 待评审的问题

1. A 该不该也覆盖 `ask` 档？（倾向：覆盖。同一层护栏，只补两档会造成新的不一致。）
2. 目标 token 要不要做 `~` / `$HOME` 展开？（倾向：`~` 要，`$HOME` 不要 ——
   前者是词法的，后者要变量求值，而求值就滑向 B 的误报面。）
3. 一条命令里多个重定向（`a > f1 2> f2`）——全部检查，还是只第一个？
4. 命中之后卡片上显示什么？显示整条命令还是只显示命中的目标？
5. 有没有比 A 更值得先做的：**把 Bash 从「全自主档自动放行」里拿掉一部分**？
   （比如：全自主档下带文件重定向的段一律降级成 ask。这不依赖任何路径规则，
   覆盖面反而更宽。代价是全自主档变吵。）
6. 我是不是把 C 判死得太早了？

# 独立评审之后的修订（v2）

评审用**真 `decide()` / 真 `splitBashSegments()`** 跑数据，推翻了我三处。
下面是修订后的结论；被推翻的原文保留在上面，不删 —— 删掉就看不出错在哪了。

## 修订 1：§1.3「整层路径护栏对 Bash 失效」说大了

病根本身成立（`permission.ts` 里 `if (p.tool !== toolName) return false`，
deny / confirm / ask 三处都过它）。但**实际敞开的口只有两个**：

| | default | acceptEdits | +allow `Bash(*)` | bypass |
|---|---|---|---|---|
| `echo x > ~/.zuse/cron/tasks.json` | ask | ask | **allow** | **allow** |
| `echo x > ZUSE.md` | ask | ask | **allow** | **allow** |

D7 那轮加的 `coversSegment`（「带重定向的段，前缀规则不算覆盖」）在 default /
acceptEdits 档**是真的在挡** —— 它不是路径护栏，但把这一类命令全数逼进 ask。

**这个限定不是措辞洁癖：它决定了修法插在 `decide()` 的哪一步。** 见修订 3。

## 修订 2：§4 问题 5 那个方案（全自主档下带重定向的段一律降级 ask）—— **不做**

评审拿真实语料数了数（CC 在本仓的 6 份 transcript，5759 条 Bash 调用）：

- `hasFileRedirect` 命中 **651 条 = 11.3%**。一个 4259 条的会话会弹 528 张卡。
  这不是「变吵」，是把全自主档变回询问档。
- **651 条里 419 条含 heredoc，其中 207 条（31.8%）的重定向标志完全来自
  heredoc 正文** —— 纯误报。绝大多数是 `git commit -F - <<'EOF'` 的中文提交信息里
  有个 `->`。今天这个误报是安全方向的（只影响 allow 前缀覆盖，掉进 ask 看不出来），
  一旦接到「弹卡」上，卡片会说「这条命令要写文件」——**那是一句假话**。
  我用「误报会训练用户闭眼点允许」枪毙了方案 B，这条同样适用，只是从 100% 降到 32%。
- **cron 会硬失败**：非交互会话是 `decision === 'allow' ? 'allow' : 'deny'`，
  而 cron 的默认档就是 bypass。11% 的 Bash 调用直接被拒，其中三分之一还是误拒。
- 覆盖面**并不比 A 宽**：它只是把同一批重定向命令从「按目标筛」变成「全弹」，
  `cp` / `tee` / `sed -i` 一样管不着。

结论：**同样宽的护栏 + 37 倍噪声 + 一条假话文案。** 不做。

（值得留的是**收窄版**：只在「目标静态判不出来」时降级 ask —— 见修订 4 第 7 条。）

## 修订 3：A **只覆盖 deny 与 confirm，不碰 ask**（推翻我 §4 问题 1 的倾向）

我原来倾向「也覆盖 ask，否则同一层护栏只补两档会造成新的不一致」。**这条会反噬。**

`ask` 是第 5 步，在 bypass（3.5）**之后** —— 加在那里对 bypass 档一点用没有，
而 bypass 正是唯一敞着的档。要有用就得挪到 bypass 之前，
**而那样一来用户手写的 ask 规则会在全自主档下开始生效**。本机的全局配置就是：

    "ask": ["Memory(save)", "Memory(delete)", "Bash(*)", "Write(./**)", "Edit(./**)"]

`Write(./**)` 一旦能被 Bash 重定向目标命中并排在 bypass 前面，**项目内每一个
`> 任何文件` 都要弹卡** —— 我在问题 5 里担心的「变吵」，从后门原样走了回来。

deny 和 confirm 都是**内建的、封闭的、路径明确的**表，没有这个问题。
「新的不一致」用一行注释解决，不用一个会让全自主档失效的对称性。

## 修订 4：A 的实现清单（评审查出五个坑）

1. **引号 = 一个字符绕过。** `echo x > "~/.zuse/settings.json"` 读出来的目标带引号，
   任何规则都不命中。目标 token 必须按**带引号态的 word** 来读 ——
   `targetIsNull` 现在的注释明写「只在引号外调用，所以不必处理引号态」，
   那个前提对目标 token 不成立。还要处理 `"my file.txt"`（读到空格就断）。
2. **`cd` 让基准 cwd 错位。** `cd ~ && echo x > .zuse/cron/tasks.json` 会被解析成
   `<会话cwd>/.zuse/cron/tasks.json`，**静默漏掉**。而 `cron/tasks.json` 正是
   `DEFAULT_DENY_RULES` 注释里点名「比改 settings 更直接」的那个文件。
   **这条要如实写成 A 的已知漏洞**，不能只写「变量拼接绕得过」。
3. **`>|` 的分段是坏的**（既存 bug，独立于本设计）：`>` 分支只做前瞻不推进 `i`，
   `|` 落到管道分支被当成分隔符。已修，见另一条提交。
4. **`hasFileRedirect: boolean` 换成 `redirectTargets: string[]`，替换而非并存。**
   留两个字段并行 = 迟早有人只更新一个。
5. **必须同步改 `isMustConfirm()`。** 它今天对 Bash 恒返回 false，
   而 `SessionManager` 是 `if (p.mustConfirm) continue` —— 用户一按「全自主」，
   A 刚弹出来的那张 Bash 卡会被**自动按成 allow**。
6. 一条命令里的**全部**重定向都要查（`cmd > /tmp/ok 2> ~/.zuse/x` 否则一行绕过）。
7. **目标含 `$` / 反引号 / 读不出正经 token → 落 ask（fail closed），不是放过。**
   实测这一类只有 6/651 ≈ 0.9%，噪声几乎为零，却堵掉「把路径塞进变量」这条最省事的绕法。
8. `~` **要展开**。理由不是「词法的所以便宜」，而是**判据要跟着真正执行它的程序走**：
   `matchPath` 刻意不展开目标侧的 `~`（因为 `Write` 的 `resolvePath` 也不展开，
   展开了会让「判定的路径」和「打开的路径」分叉），**但 bash 会真的展开**。
   这句必须进注释，否则下一个人会来「统一」它，然后重开一个洞。
9. 卡片：**命中的目标当标题 + 整条命令可展开**。只显示目标 → 用户不知道要跑什么；
   只显示整条 → heredoc 动辄上百行，看不出是哪个字触发的。
   文案写「这条命令里有一处写向 X 的重定向」，**不要**写「这条命令会写入 X」——
   后者在 `>|` 分裂和 heredoc 误报下是假话。

## 修订 5：方案 C 我判死得太早了 —— 但判死的是「ACL 那个 C」

给 C 的两条死刑理由里，「事后比对是检测不是阻止，检测到已经晚了」**不成立**。

`createSession` 调 `buildSystemPrompt` **一次**，那一刻才读 `~/.zuse/SYSTEM.md`、
逐级 `ZUSE.md`、`~/.zuse/MEMORY.md`。**这三个文件的危害不是写入那一刻兑现的，
是下一次 createSession 兑现的** —— 中间隔着一整个会话边界。
「检测到已经晚了」对 `rm -rf` 成立，对**恰恰是这三个文件**不成立。

于是有一个我漏掉的候选：

**C′：把确认从写入时挪到读取时。** `buildSystemPrompt` 组装前比对这三个文件的
hash 与「上次用户认可过的版本」，不一致就把 diff 摆出来让人点一次。

- 覆盖面**与写入路径完全无关**：Bash 重定向、`cp`、`tee`、`sed -i`、
  `python open()`、MCP 工具、变量拼接、`cd` 换基准 —— 一个不漏。
  A 那张「挡不住的等价路径」清单整个消失。
- 噪声：只在文件真变了时弹一次，一个会话最多三次。
- 不做静态分析，因此**没有「以为不漏」的风险**。
- 代价照实说：它是 detect-at-consume 不是 prevent-at-write，文件在磁盘上确实被改过；
  而且只覆盖「进系统提示词」这一类，`cron/tasks.json` 和 `settings*.json*`
  要各自在自己的读取点上挂同样的闸 —— 那是三处独立改动。

**不用 C′ 替掉 A**（A 便宜、当场拦、模型能立刻知道这条路不通），
但 C′ 是「A 之后的下一步」，另开一轮 spec。

## 修订 6：同类的洞（评审枚举了全部已注册工具）

- **`Memory`** —— 同一个洞，而且直接命中「必须确认」档保护的那个文件。
  `specifierKind: 'opaque'`（限定符是动作名），路径规则一条都命不中，
  而它 save/delete 成功后必定重写 `~/.zuse/MEMORY.md`。
  实测全自主档下 `Memory(save)` → allow。**处理见另一条提交。**
- **MCP 工具** —— 比 Bash 敞得更彻底：`buildMcpTool` **完全没有 `specifierFor`**，
  于是 specifier 恒为 null，**任何带限定符的规则对 MCP 工具都不可能命中**，
  只能写裸 `mcp__server__tool`（全有或全无）。本轮不覆盖，**但必须在文档里列出来**，
  别让「Bash 修好了」读起来像「写入面收口了」。
- **`LspInstall`** —— `spawn` 跑 `npm install`（会落盘 + 跑 postinstall），
  `opaque` 限定符，全自主档直接 allow。清单是写死的四种 npm 包，风险有限，
  但性质相同。
- 确认无写入面的：Read / Glob / Grep / WebSearch / WebFetch / TodoWrite /
  RunOutput / ScheduleWakeup / Lsp / Skill / Agent。

## 修订 7：D 已经做完了

拒绝文案已改（`agent.ts`），features.md 也已如实声明。D 不再是候选项。

## 必须如实写进文档的话（三处：代码注释 / features.md / 工具说明）

- A **只挡文件重定向**；`cp` / `mv` / `tee` / `sed -i` / `dd of=` / `python open()` /
  MCP 工具一个都不管。
- A 的目标解析是**静态**的：变量拼接、前段 `cd` 改变基准目录、heredoc 正文里的伪 `>`
  都会让它判错（`cd ~ && echo x > .zuse/cron/tasks.json` 是实测的漏例）。
- **MCP 工具完全在路径护栏之外**，本轮不覆盖。
- UI 上**不要**把这一档说成「无法绕过」。
