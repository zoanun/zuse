# 权限规则解析:连字符被拒 + 非法规则静默丢弃(回溯审计 D6)

## 一、实测复现(用这台机器上**真实存在**的工具)

```
export function parseRule(rule: string) {
  const m = /^([A-Za-z_][A-Za-z0-9_]*)(?:\((.*)\))?$/.exec(rule.trim())
```

MCP 工具名的构造是 `mcp__${serverName}__${toolDef.name}`(`mcp-registry.ts:119`),
而 **MCP 规范允许工具名带连字符**。本机 `context7` 实际暴露的就是 `resolve-library-id`
(从跑着的 daemon 的 `/api/mcp` 拉的原文)。

```
工具名: mcp__context7__resolve-library-id   parseRule → null

deny: [该工具]  mode=default      → ask     matched=-
deny: [该工具]  mode=acceptEdits  → ask     matched=-
deny: [该工具]  mode=bypass       → allow   matched=bypass     ← 规则整条蒸发
对照（同样的规则、工具名去掉连字符）  → deny  matched=<规则>    ✓
```

**deny 规则被静默丢弃。** 用户以为自己禁掉了一个工具,实际没有,且**没有任何提示**。

同类的静默失效还有:规则里多打一个空格、大小写写错、写成 `Bash (ls*)`——
全仓**没有任何地方校验规则合法性**。

## 二、两处修,第二处才是病根

### 2.1 放宽字符集

```
/^([A-Za-z_][A-Za-z0-9_.-]*)(?:\((.*)\))?$/
```

加 `-` 与 `.`。首字符仍限字母/下划线(不让规则以 `-` 开头,那更像命令行参数写错)。

**为什么连 `.` 也加**:工具名将来可能带点(命名空间形态),而放开一个字符的成本是零、
收益是不用再修一次同样的洞。**但不能放成 `.*`** —— 那样 `Bash(ls` 这种缺右括号的
写法会被当成一个「名叫 `Bash(ls` 的工具」,错得更隐蔽。

### 2.2 非法规则必须**吵**,不能静默丢

这才是这条缺陷的病根:`parseRule` 返回 null 之后,调用方一律当「不匹配」处理。
于是**一个打错的 deny 规则 = 没有这条 deny**,而用户看到的是「我配了啊」。

处置(需要拍板,见 §3):

- 所有非法规则在**设置解析时**打一条 `console.warn`,把原文逐字打出来;
- **`deny` 里的非法规则直接抛**,让 daemon 起不来。

理由是**失败方向不对称**:
- `allow` / `ask` 里写错 → **fail closed**(该放行的没放行)→ 用户会立刻发现,自己去修;
- `deny` 里写错 → **fail open**(该拦的没拦)→ 用户**永远不会发现**,直到出事。

对安全控制,「配错了就别启动」比「配错了静默降级」正确。本仓已有同型先例:
注册表遇重复键**直接抛**,理由写在 `CLAUDE.md`——「重复注册在运行期表现为
『某项神秘失效』,抛出来才能在启动时暴露」。

**代价**:一个 typo 会让 daemon 起不来。这是故意的 —— 但错误信息必须写清楚
是哪一条、哪个字符不合法、正确写法长什么样。

## 三之零、v2:三个拍板点的结论(子代理商议后直接执行)

**1. `deny` 非法就抛 —— 否决。三张表一视同仁,都只告警。**
失败面查清楚了:`loadSettings()` 的调用点包括 daemon 启动、**每建一个会话**、
**每个 `GET /api/models` / `PUT /api/model` 请求**、每次 STT/TTS、cron 触发。
抛在那里不是「开不了新会话」,是 **daemon 根本起不来** —— 而用户改配置的唯一图形入口
正是它托管的 Web UI。把「部分安全降级」换成「整机不可用 + 自救入口一并没了」,代价不对等。
`CLAUDE.md` 那条「注册表遇重复键直接抛」的先例**不适用**:那是源码级不变量、
在模块加载期触发、由开发者修;权限规则是**用户数据**,fail 时人已经在用了。

**2. 我的「allow/ask 都是 fail closed」论据是错的 —— `ask` 对只读工具 fail open。** 实测:

```
ask:["Read(~/.ssh/**)"]   → ask     ✓
ask:["read(~/.ssh/**)"]   → allow   ← 大小写写错，护栏从「弹框」变「静默放行」
```

机制:ask 表不命中就掉到 `decide` 末尾的 `tool.readOnly ? 'allow' : 'ask'`,
而 Read/Grep/Glob 都是只读 —— 「给敏感路径挂 ask」正是这类规则最典型的写法。
所以**不给 deny 开特例**,否则等于把一个错误认知固化进代码。

**3. 字符集不够,改成结构式 `^([^()]+?)\s*(?:\((.*)\))?$`。**
MCP 规范对 tool name **没有任何 pattern 约束**(schema 里就是裸 `"type":"string"`),
而 serverName 是用户写的 JSON key —— **字符集是外部输入决定的,猜不完**。
今天补 `-`,明天有人把 server 叫 `my db` 或用中文,同一个洞再修一遍。
结构式仍守住 `Bash(ls`(缺右括号)必须非法这条底线。
已知放宽:`Bash (ls*)` 由非法变生效(实测本机 41 条规则受影响 = 0);
`-x` 这类从「非法」变成「合法但永不命中」——**所以必须和第二道校验捆绑上线**。

## 三之一、评审查出的两条同源缺陷(设计稿原本没写)

**A. `buildRule` 与 `parseRule` 不互逆 → 「本会话总是允许」对带连字符的 MCP 工具完全失效。**
`decide` 用 `buildRule` 造规则存进 sessionAllow,下次 `matchesRule` 用 `parseRule`
解不出来 → 不命中 → **又弹一次框,无限循环**。更糟:「持久允许」会把这条自己都解析不了的
规则**永久写进 `settings.local.json`**。结构式一并修掉,并有往返测试钉住。

**B. 「大小写写错」是另一种机制,字符集怎么改都修不了。**
`read(x)` 解析得出 `{tool:'read'}` —— **合法**,只是没有那个工具,于是永不命中,
症状与非法规则一模一样。所以 `validateRules` 要接第二个参数(当前工具名单),
对「形状对但工具不存在」也报警。**只能告警**:MCP 工具是异步连上来的,
启动瞬间名单不全,针对暂时断线的 server 的规则会被误报 —— 文案里写明可忽略。

（`Bash(rm  -rf *)` 那种「限定符内部多空格」属第三类:规则合法、`matchCommand` 字面
前缀比不中。那是 `settings.ts` 注释里已经承认的「打地鼠」,**本次不解决**。）

## 三、原始的三个拍板点(留档)

1. **`deny` 非法就抛,会不会太狠?** 抛在哪一层?`loadSettings()` 是**每次建会话**
   都调的(不只启动),抛在那里意味着「配错一次,连新会话都开不了」。
   备选:只在 daemon 启动时校验一次 + 打横幅,运行期只 warn。
2. **要不要连 `allow`/`ask` 一起抛?** 我倾向不 —— 它们 fail closed,吵一声够了。
3. **字符集放到哪一步为止?** 只加 `-`,还是 `-` 和 `.` 都加?

## 五、测试点

1. `parseRule` 接受 `mcp__context7__resolve-library-id`、`mcp__my-db__query`;
   仍然拒绝 `Bash(ls`(缺右括号)、`-x`(以连字符开头)、空串。
2. **端到端 `decide()`**:`deny: ['mcp__context7__resolve-library-id']` 在
   **bypass 档**下必须 `deny`。—— 这条是本缺陷的直接回归锁;只测 `parseRule`
   证明不了 `decide` 那条链是通的。
3. `validateRules` 找得出非法项,且**原文逐字回传**(用户要能一眼看出是哪一条)。
4. 按 §3 的结论,补 warn / throw 的测试。
5. **变异验证**:把字符集改回去 → 第 1、2 条必须红。
