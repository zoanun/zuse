# 主画面只留问答，中间步骤进右侧抽屉（按轮次分页）

> 用户原话：「主画面，我希望只显示我输入的内容，和最终返回的内容。中间步骤，显示在侧边栏，
> 就是右侧的drawer。右侧显示一个竖向的tab页，保存所有的会话的中间内容，默认显示当前会话的
> 中间步骤，比如tool调用什么的。然后点级别的tab页，显示之前的会话的中间内容，
> 并且主画面滚动到对应的会话上」

## 0. 对需求的理解（**有一处岔路，先说清**）

「会话」读作**当前对话里的每一轮问答（turn）**，不是左侧栏那种要切换的历史会话。

依据是用户自己那句「**主画面滚动到对应的会话上**」—— 能滚过去，说明它们同在一个主画面里。
跨会话的话只能切换、无法滚动。

评审独立复核了这个读法，给了两条我没写的佐证：
「默认显示**当前**会话 / 点 tab 显示**之前**的会话」这个对举在 turn 语义下自洽，
而在 session 语义下**与左侧栏已有的会话列表重复**（`Sidebar` 早就在做「切到之前的会话」，
用户不会再要一遍）；且用户描述里没有任何「加载 / 等待 / 翻很久以前」的暗示。
唯一的反向线索是「**保存**所有的会话的中间内容」里那个"保存"字面偏持久化 —— 不足以推翻。

**若理解错了，改动面比初稿说的小得多。** 初稿写「整份设计要重做」，这句**过悲观**：
轮次切分已经是纯函数，抽屉、tab 条、滚动通道全部可复用，要换的只有 **tab 的数据源**
（从"本会话的轮次"换成"服务端的跨会话摘要"）。这一层是隔离的。

## 1. 实测事实（不是推断）

### 1.1 「点 tab → 主画面滚过去」这件事，基建已经有了

`packages/web/src/components/MessageList.tsx:23-42`：已有 `scrollToId` 机制 ——
按 `#msg-<id>` 找元素、`scrollIntoView({block:'start'})`、再放一个一次性 `flash` 高亮动画。
每一行都带 `id={'msg-' + m.id}`（同文件 :105）。

现用方是**搜索跳转**（`Shell` 的 `pendingScrollTo` / `searchJump`）。

**推论**：本需求里最像"新功能"的那一半是现成的，直接复用同一条通道，不新造滚动逻辑。
这也意味着「滚过去还会闪一下」是免费获得的。

### 1.2 「轮次」已经是一等概念

`packages/web/src/state/types.ts:24-32` 的 `isTurnOpener`，注释里点名了三个必须共用它的地方
（checkpoint/revert 锚点、分享分组、子代理面板作用域），并写明**中途插话(steer)不算轮次边界**。

`Shell.tsx:31-44` 的 `turnIdsOf` 已经实现了「从任意消息回溯到本轮的用户提问、再前进到下一轮」。

**推论**：轮次切分不需要新发明，且必须复用 `isTurnOpener` —— 否则插话会被误当成新一轮，
tab 数量凭空多出来。

### 1.3 右栏有一条硬约束，写在代码注释里

`packages/web/src/preview/Rail.tsx:44-50`：

> **三个子节点是固定槽位，不要改成数组/条件拼接**：`TodosPanel`/`AgentsPanel` 自己返回 null
> 时槽位仍在，React 按位置对齐，`RailRun` 因此不会因为「上面那块出现了」而被重挂
> （重挂 = iframe 换 document = demo 归零）。

**推论**：竖向 tab 条**不能**塞进 `.rail` 内部当条件子节点。见 §3.1 的布局取舍。

### 1.4 已有一个视图模式开关，但不是我们要的

`packages/web/src/state/store.tsx:38,71`：`mainView: 'chat' | 'cron'`。
它切的是「聊天 / 定时任务」两个**整页**，与本需求（聊天内部的详略）正交，不复用。

### 1.5 已有一个「只留问答」的过滤器，且已被测试覆盖

`packages/web/src/components/Message.tsx:37-39`：

```ts
export function isSelectableRow(m: Msg): boolean {
  return m.role === 'user' || (m.role === 'assistant' && replyMarkdown(m.parts) !== '')
}
```

分享模式(share mode)用它来「只列可分享的内容：提问 + 有正文的回复」，
纯工具轮次和系统提示被隐藏（`MessageList.tsx:80-82`）。

**推论**：主画面的精简过滤**与分享模式的过滤高度重合但不等同**（见 §2.1），
两者的关系必须在实现里写清楚，否则将来改一处、另一处莫名跟着变。

## 2. 主画面留什么、抽屉收什么

### 2.0 **正在跑的那一轮不过滤**（评审 P0-2 逼出来的核心决定）

实测 reducer 的真实行为：

- `reducer.ts:151`：`message-start` 新建一条 assistant 消息；
- `reducer.ts:152-154`：`text-delta` / `tool-use` / `tool-result` 都追加到**最后一条** assistant 消息上。

于是一个带工具的回合的时间线是：`msg A = [text]`（**用户已经在主画面读到这段**）→
同一条 A 上追加 `tool-use` → `message-start` 建 `msg B` → **A 当场不再是「本轮最后一条
有正文的消息」**。按初稿的规则，刚读到的正文会**当场消失、跳进抽屉**。每调用一次工具闪一次。

**定案：以「轮次是否已结束」分档。**

| | 主画面 |
|---|---|
| **正在跑的那一轮** | **全量显示，一个字不过滤**（含工具卡片、含中间正文） |
| **已结束的轮次** | 按 §2.1 收敛成「提问 + 最终回答」 |

**为什么这是对的，而不只是回避 bug**：跑的过程中你想看它在干什么，那正是工具卡片有价值的
时刻；跑完之后你只想看结论。**这恰好就是人读东西的方式**，而且顺带让整个「闪」的问题不存在——
因为过滤只在轮次终结那一刻发生一次，是一个稳定的收敛动作，不是逐 delta 的抖动。

**代价**：轮次结束的瞬间主画面会「收拢」一下（工具卡片折叠进抽屉）。这是**一次性的、
可预期的**动画，与初稿那种「读到一半正文没了」在体验上完全不同。收拢要有过渡，不要闪。

**对纯函数签名的影响**：§6.1 说「轮次切分 + 精简过滤的纯函数（无 React，好测）」——
它必须额外吃「这一轮结束了没有」。初稿以为只吃 `messages`，是错的。
判据用现成的：最后一轮 + `thinking === true` = 正在跑。

### 2.1 分界线（**本设计最需要拍板的取舍**）

用户说「只显示我输入的内容，和**最终返回的内容**」。严格照字面，一轮里模型在工具之间
说的那些话（「让我先看看这个文件…」）属于**中间**，该进抽屉。

| | 主画面 | 抽屉 |
|---|---|---|
| 用户提问 / 插话(steer) | ✅ | — |
| 一轮里**最后**一条有正文的 assistant 消息 | ✅ | — |
| 一轮里**中间**那些有正文的 assistant 消息 | ❌ | ✅ |
| 工具调用 / 工具结果 | ❌ | ✅ |
| 系统提示（压缩、警告、已中断…） | ✅ | — |

**为什么中间正文也收走**：它就是用户抱怨的噪音的主体。工具卡片本来就是折叠的（`ToolCall`），
真正把屏幕撑长的是模型的碎碎念。

**代价（要认，且不小）**：
- 模型有时把**关键结论**说在中间那条里（比如工具跑完先总结、再去做下一件事）。
  收进抽屉后，主画面会显得"答非所问"。
- 一轮如果**只有**中间正文、没有最终正文（例如被中断），主画面就只剩用户的问题，
  看着像模型没回话。**必须有兜底**：一轮在主画面上一条 assistant 都不剩时，
  保留该轮最后一条有正文的消息（哪怕它是"中间"的）。这条兜底要有测试。

**系统提示留在主画面**：压缩、`已被用户中断`、失败警告都是**关于这次对话本身**的，
不是模型的工作过程。上一次修图片解析静默正是为了让警告被看见，收进抽屉等于又藏起来。

#### 2.1a 过滤的粒度是**部件级**，不是消息级（评审 P0-3）

初稿那张表在两个粒度间来回横跳：「工具调用 ❌」是部件级，「最后一条有正文的**消息**」是消息级。
而实测两者是混在一条消息里的：

- `reducer.ts:129-137` `foldToolResults` 把 tool-result 部件并进**前一条** assistant 消息；
- `Message.tsx:425-451` `renderParts` 在同一条消息内按顺序渲染 text / ToolCall。

所以 assistant 消息的常态形状就是 `[text, tool-use, tool-result]`。**按消息级实现必然自相矛盾**：
§2.1 的兜底（一轮一条不剩 → 保留最后一条有正文的）会把一条**带工具卡片的消息整个**放回主画面，
当场违反「工具调用不进主画面」——而被中断的回合正是兜底唯一要服务的场景。

**定案：按部件过滤。** 已结束的轮次里，主画面保留的是「该轮最后一个有正文的 assistant 消息的
**text 部件**」，工具部件一律不进。兜底同理，兜的是 text 部件，不是整条消息。

**已知的连带风险**：`Message.tsx:434,439` 的 `blockBase` 跨 part 累加（那是代码预览
「运行」按钮序号不漂的修复，锁在 `Shell.rail.test.tsx:219`）。过滤掉中间 text part 会改变
后续 part 的 `blockBase`。**实现时必须让序号在过滤后的内容上重新连续计算**，
并补一条测试：精简模式下代码块序号仍不漂。

### 2.2 精简是**一个可关的模式**，不是唯一形态

Header 加一个开关（默认**开**，因为这是用户要的形态）。关掉 = 今天的行为，一字不差。

理由：把工具调用从主画面拿走是不可逆的信息重排，总有人（包括用手机看的时候）想要
全都在一条流里。另外这个开关也是**回归的逃生口** —— 精简模式出问题时用户能自己关掉，
不必等我改。

开关状态存 `localStorage`，不进服务端（它是浏览器端的观感偏好，不该跟着会话走）。

## 3. 右侧：竖向 tab + 步骤面板

### 3.1 布局（**初稿放错了地方，评审 P0-1/P1-2 推翻**）

初稿把 `StepsPanel` 作为 `.rail` 的第一个固定槽位。**这是错的**，两个理由：

1. **抽屉根本不会出现。** `Shell.tsx:73` `const hasRail = !!activeRun || showTodos ||
   runningAgents > 0`，`:380` 是 `{hasRail ? <Rail/> : null}`。初稿全篇没提 `hasRail`。
   而「看完回复想翻工具调用」的时刻，这三个条件通常一个都不成立 → 右栏不存在 → 功能等于没做。
   而若改成 `|| hasSteps`，只要这个会话调用过一次工具 `hasSteps` 就**永远为真**（步骤来自
   历史消息，不会自愈），右栏从此常驻，还会改变 `Shell.rail.test.tsx:311`
   「待办全部完成 → 右栏关掉，不留空壳」所锁的语义。两条路都有代价，初稿一条都没选。
2. **槽位数一变就会重挂预览。** §5 初稿那条「精简模式关 → DOM 与今天完全一致」的措辞会
   直接诱导实现者写成 `{clean ? <StepsPanel/> : null}` —— 那一刻 `RailRun`（`Rail.tsx:61`）
   位置漂移，PreviewFrame 重挂，demo 归零。正是 `Rail.tsx:47-49` 那条注释在防的事。

**定案：步骤抽屉整体搬到 `.rail` 外面，与它平级，`.rail` 内部一个字不动。**

```
.main-body
├── main.chat            聊天（精简后）
├── aside.rail           现有右栏：待办 / 子代理 / 预览 —— 完全不碰
└── section.steps        新增，独立一列
    ├── div.steps-body   当前选中轮次的步骤
    └── nav.turn-tabs    竖向 tab 条，贴最右
```

这样 P0-1 和 P1-2 一起消失：`hasRail` 不用动、`Rail` 的槽位不用动，步骤列自己决定何时出现
（`hasSteps` 只管自己这一列）。

**窄屏（评审 P1-1）**：`styles.css:127,144` 有一条 `@container (max-width: 900px)
{ .main-body.rail-narrow .rail { display: none } }`，而没有预览时 `railNarrow` 恒真
（`Shell.tsx:76`）。初稿若把步骤放进 `.rail`，**窄窗口下工具调用会两边都看不到**
（主画面收走了、右栏被隐藏了）—— §2.2 还恰好写了「包括用手机看的时候」，方向正好反了。

搬出来之后步骤列有自己的响应式规则：窄行下**不隐藏**，改成覆盖式抽屉（点 tab 条展开、
点外部收起）。**绝不允许出现「两边都没有」的状态** —— 这是本次布局的硬约束。

### 3.1a 落选：复用 `ManageDrawer` 那种 slide-over

评审提出的替代方案，值得记下来。`ManageDrawer.tsx:18-28` 已经是「panel 枚举 + 一排 nav tab
+ `activePanel`/`onSelectPanel`」，`styles.css:466` 是右侧 `translateX(100%)` 覆盖层，
挂在 `.shell` 层、完全在 `.main-body` 之外。用户原话用的词也正是 **drawer**。

**为什么不选**：它是**覆盖式**的（760px 宽），打开时盖住聊天区 —— 而本需求的核心动作之一是
「点 tab **主画面滚过去**」，滚到一个被盖住的地方毫无意义。常驻分栏才配得上这个交互。

代价：要自己写响应式，不能白拿 ManageDrawer 现成的 CSS。接受。

### 3.2 tab 的样子与顺序

- 一轮一个 tab，**从上到下 = 从旧到新**，与主画面滚动方向一致。
- 标签：轮次序号 + 用户提问前 12 字（截断加省略号）。纯序号认不出是哪一轮。
- **只给有中间步骤的轮次出 tab**。一轮如果没调过工具、也没有中间正文，它没有"中间内容"，
  出一个点开是空的 tab 属于骗人。
- 数量不设上限，tab 条自己滚。长对话下这条会很长 —— **接受**，因为截断会让"保存所有轮次"
  这个诉求失效。

### 3.3 默认选中与自动跟随

- 默认选中**最新的有步骤的轮次**（用户原话「默认显示当前会话的中间步骤」）。
- 新一轮开始产生步骤时**自动跟过去** —— 但**用户手动点过别的 tab 之后就不再自动跟**，
  直到他点回最新的那个（或发出新消息）。

  这条是必须的：不加，用户翻看第 2 轮的步骤时会被新流进来的内容一把拽走，根本读不完。
  与「滚动列表粘底」是同一个交互模式。

- **补：选中的轮次不存在了 → 立刻回到自动跟随**（评审 P1-4）。

  初稿只给了两个恢复条件（点回最新、发新消息），漏了「选中项消失」这一类：
  切会话（`Shell.tsx:61` 的 `useEffect(closeRun,[currentSessionId])` 只清预览，不清这个）、
  `/clear`、revert 把选中那一轮删掉。落进去之后抽屉空白，而用户**没有「最新 tab」可点**
  （tab 条已经换成新会话的了），只能靠发一条新消息解锁 —— 一个"看着像坏了"的状态。

  不是永久死锁，但必须补。判据：选中的 turn id 不在当前 tab 列表里 → 复位。

### 3.4 点 tab 的两个动作

1. 步骤面板换成该轮内容；
2. 主画面滚到该轮的**用户提问**那一条（不是最后一条回复）——
   §1.1 的 `scrollToId` 通道，锚点取 `turnIdsOf(...)[0]`，与分享模式选中时的锚点取法一致
   （`Shell.tsx:211` 已经是这么做的）。

### 3.5 步骤面板内部

按**时间顺序**混排该轮的工具卡片与中间正文 —— 抽屉的价值就是"这一轮到底发生了什么"，
按类型分区会打乱因果。工具卡片复用现有 `ToolCall` 组件，不新写一套渲染。

### 3.6 搜索跳转必须跟着改（评审 P1-3）

`packages/server/src/search/SearchService.ts:18-27` 索引的是**所有** user/assistant 的
text 块 —— 包括那些「让我先看看这个文件…」的中间正文。精简模式下它们不在主画面，于是
`MessageList.tsx:30-31`：

```ts
const el = document.getElementById('msg-' + scrollToId)
if (!el) return // 目标不在(索引不匹配/会话被截短等):静默跳过
```

**点搜索结果什么都不会发生。** 初稿对搜索一个字没提。

**定案：跳转目标落到该消息所属轮次的 opener 上，同时把抽屉切到该轮。**
理由：命中的内容本来就在抽屉里，把用户送到"能看到它"的地方，而不是送到一个不存在的锚点。
不选「跳转时临时退出精简」——一次搜索把整个视图形态改掉，副作用太大且难撤销。

### 3.7 retry / 页脚 / 流式标记的归属（评审 P1-6）

`MessageList.tsx:45-48` 的 `lastAssistantId`（retry 按钮）、`:52-55` 的 `streamingId`
（代码预览运行按钮的禁用）、`:66-76` 的 `turnFinalIds`（复制/分享页脚）**全部算在原始数组上**。
精简模式把最后一条 assistant 消息移进抽屉时（被中断、纯工具收尾），retry 按钮会跟着进抽屉
或直接消失。

**定案：这三者一律算在原始数组上，然后挂到主画面里代表该轮的那一行。**
过滤是**渲染层**的事（在 `MessageList` 内部，与 `shareMode` 同一层），不改这三处的计算输入。
`streamingId` 尤其不能动 —— §2.0 已经规定正在跑的那一轮不过滤，它本来就全在主画面。

## 4. 明确不做

- 不做跨会话的中间步骤存档（§0 的理解若成立，就不需要；若不成立，另开 spec）。
- 不做步骤的搜索/过滤。先看实际用起来找不找得到东西。
- 不改 `isSelectableRow` 与分享模式的行为。精简过滤是**另一个函数**，
  哪怕两者眼下逻辑相近 —— 合并会让「改分享导出顺手改坏主画面」变成可能。
- 不持久化"当前选中哪个 tab"。刷新回到最新，符合默认语义。

|---|---|
| 精简模式关 → **`.stream` 的子节点序列与今天逐个一致** | §2.2 的逃生口。**措辞要这样写**：初稿写「DOM 与今天完全一致」会诱导实现者去动 `.rail` 的槽位（评审 P1-2），而过滤应当只发生在 `.stream` 里面 |
| **切换精简开关时，预览 iframe 的 token 不变**（不重挂） | §3.1 的教训。现有 `Shell.rail.test.tsx:379` 只覆盖「待办出现/消失」这条路，**覆盖不到精简开关** |
| **正在跑的那一轮全量显示**：流式中工具卡片就在主画面 | §2.0，最核心的一条 |
| **轮次结束后才收敛**：同一份数据，`thinking` 由真变假 → 工具卡片从主画面移走 | §2.0 的另一半。这两条合起来才钉得住「不闪」 |
| 精简模式下代码块序号仍不漂 | §2.1a 认领的连带风险（`blockBase`） |
| 搜索命中中间正文 → 跳到该轮 opener，且抽屉切到该轮 | §3.6，否则点搜索结果毫无反应 |
| 选中的轮次消失（切会话 / revert）→ 复位到自动跟随 | §3.3 补的那条 |
| 精简模式开 → 工具卡片不在主画面、在步骤面板里 | 核心 |
| 一轮有多条 assistant 正文 → 主画面只留最后一条 | §2.1 |
| 一轮**只有**中间正文（被中断）→ 主画面仍保留一条，不是空的 | §2.1 那条兜底 |
| 系统提示（warn / 压缩摘要）留在主画面 | §2.1，防后人"顺手"一起收走 |
| 插话(steer) 不产生新 tab | §1.2，`isTurnOpener` 复用 |
| 没有工具也没有中间正文的轮次 → 不出 tab | §3.2 |
| 点第 2 轮 tab → 派发的 scrollToId 是该轮**用户提问**的 id | §3.4 |
| 手动点过旧 tab 后，新步骤流入**不**改变选中 | §3.3，最容易漏 |
| 手动点回最新 tab 后，自动跟随**恢复** | §3.3 的另一半 |

**变异验证——要两个方向，不是一个。** 初稿写「改成无条件跟随，确认那两条变红」，
评审算过：**只有第一条会红**。「点回最新 tab → 自动跟随恢复」在无条件跟随下**照样绿**。
我自己点名了这是最容易纸糊的一条，给的方案却恰好漏掉纸糊的那一半 —— 与上次 checkbox
同一个错误。

| 变异 | 应当变红的 |
|---|---|
| 改成**无条件跟随** | 「手动点过旧 tab 后不被拽走」 |
| 改成**永不自动跟随** | 「点回最新 tab 后恢复跟随」 |
| 把 §2.0 的「轮次是否结束」判据写死为 true | 「正在跑的那一轮全量显示」 |

**另需澄清（评审 P1-5）**：§3.3 说恢复条件含「或发出新消息」，而测试「手动点过旧 tab 后
新步骤流入不改变选中」若用「用户发新消息 → 产生新步骤」来造数据，正确实现**应当**恢复跟随，
这条测试反而会红。两句话对「新步骤从哪来」没区分。

**定案**：测试必须用**同一轮内继续流入的新步骤**造数据（不是新消息），
「发出新消息」是明确的恢复信号，两者不可混用。

## 6. 落地顺序

**阶段一（可独立交付、独立验证）—— 只做「主画面变干净」**

1. 轮次切分 + 精简过滤的纯函数。签名含「该轮是否已结束」（§2.0），按**部件**过滤（§2.1a）
2. `MessageList` 内部接上过滤（与 `shareMode` 同一层，§3.7）+ Header 开关 + localStorage
3. **真浏览器验证**：跑一轮带多次工具调用的对话 —— 流式中全量、结束后收拢、**中途不闪**

到这里用户就已经拿到「主画面只显示问答」了，工具调用暂时**只是折叠**在原位。
评审建议把它标成一个可交付切片而不是纯内部步骤，采纳 —— 这样即使阶段二出问题，
前半个诉求已经落地且可以单独回滚。

**阶段二 —— 步骤抽屉**

4. `.steps` 独立一列（**在 `.rail` 外面**，§3.1）+ 竖向 tab 条 + 窄屏覆盖式规则（P1-1）
5. 接 `scrollToId`（§3.4）+ 搜索跳转改造（§3.6）
6. 自动跟随 + 手动接管 + 选中项消失的复位（§3.3）
7. **真浏览器验证**：点旧 tab 是否滚过去且高亮、流式中翻旧 tab 会不会被拽走、
   **窄窗口下工具调用是否仍然够得着**（P1-1 的硬约束）、切会话后抽屉是否复位
